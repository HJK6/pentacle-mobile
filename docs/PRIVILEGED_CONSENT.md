# Face ID approvals

Signing into Pentacle grants no Approval key or lifecycle authority. Setup starts only when an authenticated host operator chooses this phone's credential and sends **Set up Approval key on phone**, or runs `agent-orch consent-key offer --credential <id>` from the daemon host. There is no Approval key section in Settings, code or fingerprint readback.

The app automatically presents a pending setup or approval request while unlocked. Expo→APNs also delivers a generic OS notification. Open the exact request, then choose **Set up with Face ID** / **Not now**, or review the exact privileged action and **Approve with Face ID** / **Deny**. Setup succeeds as **Approval key ready**; each new signature asks for Face ID. Replacing a key preserves the old active key until acceptance succeeds atomically. Already enrolled keys and saved native metadata survive an upgrade; signing in again never forces enrollment.

An offer or approval intent lasts 24 hours. Receiving, reading, prefetching, reconnecting and background delivery start no signing clock. Only explicitly opening that request starts its challenge, capped at 120 seconds or the durable deadline. Duplicate open keeps the same deadline; explicit reopen after timeout changes the nonce/id. Each audience phone has its own challenge, and only one parent approval can apply the immutable lifecycle action.

The app saves native key tags and exact signed replies before sending, scoped to host + authenticated credential + offer/request. An explicit retry after an ambiguous response reuses its exact tuple or reconciles the exact receipt first. Reconnect never signs or sends automatically. Host/account changes block old tuple transmission; forged push hints cannot switch hosts or grant authority. A mismatched receipt cannot report setup or approval success. A subsequently revoked key remains revoked on receipt replay.

The native module retains P-256 Secure Enclave, `privateKeyUsage | biometryCurrentSet`, and `WhenPasscodeSetThisDeviceOnly`. Each signature uses a fresh Face-ID-only authentication context without reuse or passcode fallback. Face ID cancellation leaves the request pending; lockout requires unlocking Face ID before retrying. The daemon verifies possession of the credential-bound public key, not remote biometric/hardware attestation or ownership of a supplied push token. A copied operator credential can race the intended phone for the first valid setup response; conflicting valid replies produce one host/phone security notice and a review route.

For a missing, invalidated or revoked key, ask the host to send a fresh targeted setup offer. The host can review `consent-key status <offer-id>`, list keys, and revoke with the existing daemon-host recovery CLI. Also revoke a lost phone's operator credential. Key loss/revocation does not revoke an existing lifecycle grant; ordinary/emergency lifecycle-revoke rules still apply. No Settings recovery or forced replacement is added.

The [shared framing fixture](../tests/fixtures/consent-offer-transcript.json) uses uint32 big-endian UTF-8 byte lengths, including the new enrollment domain. Challenge expiry is integer Unix seconds in decimal; absent prior key is an empty string. Lifecycle signature framing is unchanged. Retired code/prepare/enroll/confirm routes refuse; pending legacy ceremonies cannot become active during migration.

Configure the ignored local `apple.easProjectId` and optional `apple.pushEnvironment` to match the signed app and its APNs entitlement. Development is the default, preserving the installed development signing profile. The daemon sender uses the same project UUID through `EXPO_PROJECT_ID` and any project-required `EXPO_ACCESS_TOKEN`. Registration binds the current host/credential/token/project/environment through fresh authentication. Old globally registered tokens cannot receive consent push. Permission denial, missing registration/config or provider failure is visible to the issuer as degraded delivery. Rotation and invalid-token cleanup affect only the owning binding. An offline account switch cannot take over a token still bound to another credential; host recovery is required if its unregister could not be delivered.

A notification tap is an untrusted navigation hint. Unlock, reconnect and fresh audience authentication precede reading/opening the exact request. Consent taps never land on generic Updates or Settings and cannot change hosts. In-app automatic presentation is the fallback. Expo tickets and receipts prove transport/provider handoff; they do not prove physical OS display. The actual provider receipt and agent-accessible device screenshot are delivery-window evidence, recorded separately.

Tests use isolated identities and real daemon P-256 verification. Simulator signer fixtures prove the product/protocol with observed simulator biometrics, not Secure Enclave or a new physical-device ceremony. Device signer policy is unchanged; the operator's existing physical-test waiver remains effective. No manual test checklist or forced setup is required.
